# ERP TOURECHE

نظام إدارة متاجر **الدفع عند الاستلام** في الجزائر: من الطلبية إلى التسليم، ومن المنتج إلى الإعلان، مع **مستشار** يحلل بياناتك ويقترح ما تفعله.
Système de gestion pour boutiques **COD** en Algérie : de la commande à la livraison, du produit à la pub, avec un **Conseiller** qui analyse vos données.

> يعمل 24/7 على **VPS** (Docker بجانب n8n، انظر أدناه) أو على جهازك (macOS / Windows / Linux)، وتفتحه من هاتفك كتطبيق.
> Tourne sur votre ordinateur et s’ouvre sur le téléphone via **Tailscale**, comme une application.

## التثبيت · Installation

**المتطلبات:** [Node.js 22+](https://nodejs.org) وجهاز يبقى مشغلاً.

```bash
# 1) انسخ المجلد «ERP TOURECHE» إلى جهازك ثم:
npm run setup      # يثبّت ويبني الواجهة (مرة واحدة)
npm start          # يشغّل الـ ERP على http://localhost:3600
```

أو بنقرة: `start.command` (macOS) · `start.bat` (Windows) · `start.sh` (Linux).

أول مرة تفتح الصفحة يطلب منك: حساب المدير، **كلمة مرور العمليات الحساسة** (مختلفة عن كلمة الدخول)، وأول مشروع.

### الفتح من الهاتف كتطبيق (Tailscale)

1. ثبّت [Tailscale](https://tailscale.com/download) على الجهاز وعلى الهاتف وسجّل بنفس الحساب.
2. على الجهاز: `tailscale serve --bg 3600` ← يعطيك رابطاً آمناً مثل `https://your-pc.tailXXXX.ts.net`.
   ضع `ERP_TRUST_PROXY=1` في ملف `.env`.
3. افتح الرابط على الهاتف ← «إضافة إلى الشاشة الرئيسية» ← يعمل كتطبيق بملء الشاشة.

> لا تفتح منفذ الراوتر. Tailscale يكفي ويبقي الـ ERP خاصاً بك.

### إبقاؤه شغالاً

- **macOS:** إعدادات النظام ← البطارية ← منع السكون عند توصيل الشاحن؛ أو `caffeinate -dimsu &`.
- **Windows:** خيارات الطاقة ← السكون: أبداً؛ وأضف `start.bat` إلى «برامج بدء التشغيل».
- البديل: `npx pm2 start server/index.js --name erp && npx pm2 save`.

## التشغيل 24/7 على VPS (Hostinger) بجانب n8n

الـ ERP يعمل في حاوية Docker مستقلة على نفس الخادم، خلف Traefik الموجود مع n8n، بدومين فرعي و HTTPS تلقائي. حاوية n8n لا تُلمس.

1. **الدومين:** أضف سجل `A` باسم `erp` (مثلاً `erp.leadsauto.cloud`) ← عنوان IP الخادم، من حيث تدير DNS الدومين. مع Cloudflare: اجعله «DNS only» حتى تصدر الشهادة.
2. **على الخادم** (hPanel ← VPS ← Browser terminal، أو SSH):
   ```bash
   git clone -b claude/erp-toureche-system-fdir8x https://github.com/ouss-trch/my-profil.git /opt/erp
   bash "/opt/erp/ERP TOURECHE/deploy/install-vps.sh" erp.leadsauto.cloud
   ```
   السكربت يقرأ إعداد Traefik من حاوية n8n (الشبكة، المنافذ، الشهادة)، يتحقق من الدومين، يبني الـ ERP ويشغّله (بضع دقائق)، ثم يتأكد أنه يعمل ويضيف الأمر القصير `erp`. **لا تنشر قالب Traefik من Docker Manager**: Traefik موجود أصلاً مع n8n، ونسخة ثانية تتنازع المنفذين 80/443.
3. افتح `https://erp.leadsauto.cloud` ← **رمز الإعداد** الذي طبعه السكربت (أو `bash deploy/erp.sh setup-token`) + حساب المدير + كلمة المرور الحساسة + أول مشروع. الرمز يمنع أي شخص يصل إلى الرابط قبلك من إنشاء حساب المدير، ويُحذف بعد الإعداد. في الإعدادات ضع «الرابط العام لاختبارات الصفحات» = `https://erp.leadsauto.cloud`.
4. **نقل بياناتك من الحاسوب** (إن كان لديك): انسخ آخر ملف `toureche-YYYY-MM-DD.db` وملف `data/.secret-key` إلى الخادم ثم:
   ```bash
   bash deploy/erp.sh restore /root/toureche-2026-10-26.db
   bash deploy/erp.sh import-key /root/.secret-key
   ```
5. **n8n ↔ ERP على نفس الخادم:** من n8n استعمل `http://erp-toureche:3600/api/hooks/<slug>/orders` (شبكة داخلية، أسرع ولا يمر عبر الإنترنت).

| الأمر | ماذا يفعل |
|---|---|
| `erp update` (أو `bash deploy/erp.sh update`) | نسخة احتياطية ← آخر نسخة من GitHub ← بناء ← فحص التشغيل (رجوع تلقائي للنسخة السابقة إن لم تشتغل) — البيانات لا تتأثر |
| `erp status` · `erp logs` | الحالة · آخر السجلات |
| `erp backup` | نسخة احتياطية الآن |
| `erp restore FILE.db` | استرجاع (يتحقق من الملف، يحفظ القاعدة الحالية، ويعيد تشغيل الـ ERP في كل الحالات) |
| `erp reset-password USER PASS` | كلمة مرور منسية |
| `erp setup-token` | رمز الإعداد الأول (قبل إنشاء حساب المدير فقط) |

**التحديث من داخل الـ ERP (بدون SSH):** الإعدادات ← النظام ← بطاقة «تحديث الـ ERP»: النسخة الحالية، آخر تحديث ونتيجته، والتغييرات الجديدة على GitHub، وزر **تحديث الآن** (بكلمة المرور الحساسة). الزر ينفّذ نفس `erp update` بخطواته وسجله، والـ ERP يغيب دقيقة تقريباً أثناء إعادة التشغيل.
- كيف يعمل: الحاوية لا تستطيع تحديث نفسها، فتكتب طلباً في `/var/lib/erp-updater/inbox`، وخدمة systemd على الخادم (`erp-updater.path`) تنفّذه وتكتب النتيجة في `/var/lib/erp-updater/state` (الحاوية تقرؤها فقط). مؤقّت `erp-updater.timer` يبحث عن نسخة جديدة كل 6 ساعات.
- التفعيل مرة واحدة: نفّذ `erp update` من SSH **مرتين** (الأولى تجلب السكربت الجديد، والثانية تثبّت الخدمة وتبني الصورة برقم النسخة). بعدها كل التحديثات من الزر.
- الفحص: `systemctl status erp-updater.path` · سجل آخر تحديث في البطاقة نفسها أو `journalctl -u erp-updater`.

**النسخ خارج الخادم (Google Drive عبر n8n):** البيانات في volume `erp-toureche_erp_data`. كل ليلة (03:00) يضغط الـ ERP نسخة اليوم ويرسلها إلى سير العمل «Toureche ERP · نسخ احتياطي إلى Google Drive» في n8n، فيرفعها إلى مجلد `TOURECHE-ERP-backups` في Google Drive ويُبقي آخر 30 نسخة (الأقدم تذهب إلى سلة المهملات).
1. في n8n: تأكد أن حساب **Google Drive account** متصل، وأن سير العمل مفعّل.
2. في الـ ERP: الإعدادات ← عام ← n8n ← **Webhook النسخ الاحتياطي (Google Drive)** = رابط الـ Webhook (Production URL) من سير العمل. الرابط فيه رمز سري: لا تنشره.
3. الإعدادات ← النظام ← **نسخة احتياطية الآن**: يجب أن تظهر «يعمل». لا تُعدّ النسخة محفوظة إلا إن أكّد n8n وصولها إلى Drive، وأي فشل يظهر في البطاقة وفي المستشار.
4. احفظ محتوى المفتاح السري في مدير كلمات المرور (بدونه تبقى الطلبيات والزبائن، لكن تُعاد مفاتيح الربط يدوياً): `docker exec erp-toureche cat /data/.secret-key`

وفعّل أيضاً النسخ الاحتياطي للـ VPS من hPanel.

الحقول المدعومة: `customer_name, phone, wilaya, commune, address, delivery_type, items[], total, utm_source, utm_campaign, utm_content, landing_url, event_id` (`event_id` = معرّف حدث Purchase في المتجر، تُربط به أحداث «أُكّدت / سُلّمت» إلى Meta).

**جدول SOU9NA Orders (يكتبه سير COD في n8n):**
- ورقة `customer`: كل طلبية وكل نموذج متروك بأعمدة إنجليزية. يقرؤها الـ ERP والتقرير الصباحي، وعمود `landing_page` فيها ينسب الطلبية لصفحة الهبوط.
- ورقة `Orders`: سطر عربي واضح لكل طلبية فقط: التاريخ بتوقيت الجزائر، رقم Shopify، الحالة، الزبون، العنوان، المنتج، الأسعار، صفحة الهبوط. السطر الأحمر طلبية لم تُنشأ في Shopify.
- ربط الـ ERP بالجدول: الإعدادات ← عام ← n8n: رابط «جسر Google Sheets» ومفتاحه (من عقدة Authorize في سير الجسر). ثم في تكاملات المشروع: «مزامنة الجدول» + معرّف الجدول (أو الصق رابط الجدول كاملاً؛ المسافات تُحذف تلقائياً) + اسم الورقة `customer`. الجسر في n8n لا يقبل إلا الجداول المسموحة فيه (SOU9NA Orders و autoparts-58): جدول جديد يجب إضافته إلى قائمة `ALLOWED` في سير «Toureche ERP · جسر Google Sheets». الطلبيات التي لم تُنشأ في Shopify تدخل الـ ERP بوسم `not-created-in-shopify`.
- **Client secret في مكانين:** إن غيّرته في Dev Dashboard فحدّثه في الـ ERP وفي n8n (Credentials ← «Shopify SOU9NA»). وإلا ترفض Shopify كل طلبية (`Missing or invalid client secret`)، فلا تصل إلى Shopify ولا إلى الـ ERP، بل إلى الجدول وتيليغرام فقط.

## صفحات الهبوط بالذكاء الاصطناعي (صفحات المتجر ← «إنشاء صفحة هبوط»)

صفحة المنتج تبقى للإعلان والمنشور الرئيسيين. صفحة الهبوط لزاوية واحدة لجمهور واحد: منتج واحد، بلا قائمة ولا تذييل، بنفس نموذج الطلب والعروض. صفحة الهبوط **مخفية**: قالب منتج إضافي لا يظهر في القوائم ولا المجموعات، ولا يفتحه إلا رابطه. صفحة المنتج العادية لا تتغير لأحد.

0. **التوصيل والسياسات** (البطاقة الأولى في صفحات المتجر ← «تحديث من المتجر»): أسعار المكتب والمنزل لكل ولاية من إعداد القالب `shipping_table` (نفس مصدر نموذج الطلب؛ دون `read_themes` يقرأ جدول `/pages/delivery` العام)، ونصوص المعاينة والاسترجاع والشحن من `/policies/…`. اكتب **مدة التوصيل** التي تلتزم بها؛ الـ ERP يقترح المدة المقاسة من طلبياتك المسلّمة (الوسيط و80%). الكاتب يستعملها كما هي: **التوصيل إلى جميع الولايات** (ما لا تغطيه شركة تغطيه أخرى؛ لا يُعرض «51 من 58»)، «المكتب من… المنزل من…»، والشروط والمدد من السياسات. ولاية بلا سعر في جدول القالب يرفضها نموذج الطلب في المتجر، فتظهر في البطاقة كملاحظة منفصلة لتضع لها سعراً (لا يغيّر الـ ERP القالب ولا يخمّن سعراً).
1. اختر المنتج: **يحلّل Claude صفحته فوراً** (العنوان، الوصف، المواصفات، الألوان، الصور، السعر، عروض الكمية) ويعرض في مكان الزوايا:
   - **ما وجده في صفحة المنتج**: كل حقيقة يمكن إثباتها وفائدتها للزبون.
   - **أسئلة يطرحها الزبون ولا تجيب عنها الصفحة** (التسرب، مدة حفظ الحرارة، العمر المناسب…)، ولكل سؤال زر **«أجب»** و**«لا يهم»**. السلسلة كلها من مكان واحد:
     1. **جوابك خاصية للمنتج، لا سؤال شائع.** يصوغه Claude (ولو كتبته بالدارجة) دون إضافة أي معلومة، ويُحفظ في **بطاقة المنتج**: سطر في «جدول المواصفات» («مانع للتسرب: نعم») + **سطر ميزة** الفائدة فيه أولاً («غطاء ومصاصة مضادان للتسرب: الحقيبة تبقى جافة»). التعديل اليدوي (القلم) يحفظ الخاصية والقيمة والميزة كما تكتبها. جواب لا يعطي قيمة («موجود في الصورة») يُرفض مع ما ينقصه.
     2. **صفحات الهبوط** تستعمل الأجوبة خصائص مؤكدة (`owner_facts`): في الأدلة وتسلسل الصور عند تحليل الزوايا، في النقاط والفوائد عند الكتابة، وفي **الصور الوصفية** (كل خاصية تخدم الزاوية تظهر في صورة على الأقل: تسمية في صورة «المزايا» أو صورة «ميزة تُرى»)، وتصل إلى وصف كل صورة يرسمها المولّد. **لا تُكتب أسئلةً شائعة**: الأسئلة الشائعة لاعتراضات الشراء فقط (التوصيل، الدفع، المعاينة، الاستبدال، المقاس أو اللون). و**SEO** بالذكاء الاصطناعي يضعها في المواصفات والمميزات ولا يحذفها.
     3. **«انشر الأجوبة في صفحة المنتج (Shopify)»** (كلمة المرور الحساسة) يضيف لكل جواب سطراً في «المواصفات» وميزة في «المميزات» بوصف المنتج الحي، ويحذف نسخها القديمة من «أسئلة شائعة» (كانت الأجوبة تُنشر هناك قبل هذا التحديث؛ ويُحذف عنوان القسم إن فرغ)، دون لمس السعر والصور وبقية النص. جواب قديم بلا سطر ميزة يصوغه Claude مرة واحدة عند النشر. وكل «نشر» عادي للمنتج من الـ ERP يحملها أيضاً.
     4. **«حدّث الزوايا بالأجوبة الجديدة»** يعيد التحليل: لا يعيد طرح ما أجبت عنه أو قلت إنه لا يهم.
   - نفس الأسئلة في بطاقة المنتج (المنتجات ← المنتج ← «أسئلة الزبائن عن هذا المنتج»). حذف سطر الجواب من المواصفات يعيد السؤال مفتوحاً.
   - **4 إلى 6 زوايا خاصة بالمنتج** (لا كلمات عامة): مثلاً لترمس أطفال «مشروب دافئ حتى الاستراحة» بدل «الاستعمال اليومي». لكل زاوية: الجمهور، **مستوى وعيه** (لا يعرف المشكلة بعد، يعرف المشكلة، يعرف الحلول، يعرف المنتج: منه تبدأ الصفحة)، **كلماته** كما يقولها الزبون، الوعد (العنوان، يجتاز اختبار «الآن يمكنك…»)، الآلام، الأدلة من الصفحة ومن أجوبتك، الاعتراضات، الإطار والتصميم المناسبان، و**تسلسل صور الصفحة** (الخطاف ثم صورة لكل فكرة).
   - اختيار زاوية يضبط الإطار والتصميم والجمهور والرابط تلقائياً (تُغيَّر في «الإطار والتصميم»). التحليل محفوظ (جدول `product_insights`) ولا يُعاد إلا إن تغيّرت صفحة المنتج أو ضغطت «حلّل من جديد». الزوايا العامة والزاوية المكتوبة يدوياً تبقى متاحة.
   - أطر الكتابة: **AIDA** (جمهور بارد)، **PAS** (يعرف المشكلة)، **BAB** (يغيّر روتيناً)، **FAB** (منتج تقني)، **4P** (جمهور متردد)، **FOMO الصادق** (عرض كمية حقيقي أو مخزون قليل فعلاً).
2. **تصميم حسب الزاوية** (تلقائي، أو اختره يدوياً عند الإنشاء): لكل زاوية ترتيب أقسام ولون وأقسام خاصة بها، لا قالب واحد للجميع:
   - **هدية**: الصورة أولاً بخلفية دافئة، «هدية مناسبة لـ» (المناسبات)، معرض الصور، ثم الفوائد.
   - **المشكلة والحل**: المشكلة أولاً بتنبيه، جدول «بدونه / معه»، ثم الحل.
   - **الاستعمال اليومي**: «يوم كامل معه» (الصباح، المدرسة، المساء) وصورتان أثناء الاستعمال.
   - **القيمة / السعر**: جدول المواصفات، معرض، مقارنة، ثم الضمان مبكراً.
   - **العائلة**: لحظات العائلة، معرض، ثم المناسبات.
   - **كلاسيكي** لبقية الزوايا. شريط الثقة (الدفع عند الاستلام، التوصيل إلى N ولاية، مكالمة التأكيد…) تحت العنوان في الكل.
3. Claude يكتب (بتحليل الزاوية المختارة: وعدها في العنوان، آلامها في الفقرات، أدلتها في الفوائد، اعتراضاتها في الأسئلة): عنوان يطابق الزاوية، فقرات الإطار، الفوائد، خطوات الطلب، الضمانات، 4–6 أسئلة شائعة، وزر الطلب. القواعد ثابتة: لا أرقام ولا آراء ولا ندرة ولا ادعاءات صحية مختلقة (سياسة Meta)، العروض والسياسات كما في صفحة المنتج بالضبط، وما ينقص يظهر في «ما يحتاج منك».
4. **نشر على المتجر** (كلمة المرور الحساسة) يكتب في القالب المنشور: `layout/erp-landing.liquid` (theme.liquid دون الرأس والتذييل)، `sections/erp-lp.liquid` (النصوص، قابلة للتعديل من محرر القالب)، و`templates/product.lp-<slug>.json` (قسم المنتج نفسه بنموذج الطلب والعروض)، ثم تحويلة **`/pages/<المنتج>-<الزاوية>`** إلى `/products/<handle>?view=lp-<slug>`. Shopify لا يقبل «/» ثانية داخل اسم الصفحة، والتحويل يمرّر معاملات الإعلان.
5. ضع الرابط في حملة الزاوية نفسها. الطلبيات تُنسب للصفحة في «صفحات المتجر»، ولمقارنتها بصفحة المنتج: اختبار A/B.

**الـ ERP هو المرجع:** «سحب من المتجر» يحذف القالب والرابط ويُبقي الصفحة في الـ ERP لإعادة نشرها. «حذف» (كلمة المرور الحساسة) يحذفها من الـ ERP **ومن المتجر معاً**: القالب، الرابط `/pages/…`، صورها المرفوعة، الصفحة المثبتة، وتُعطَّل نسختها في اختبار A/B (ويتوقف الاختبار إن لم تبقَ فيه صفحتان). الطلبيات وزياراتها تبقى. وإن فشل نشر أول بعد كتابة القالب، يُحذف القالب فلا تبقى صفحة نصف منشورة.
بطاقة صفحات الهبوط تقارن الـ ERP بالمتجر عند كل فتح: بقايا صفحات في Shopify لم تعد في الـ ERP، قالباً أو رابطاً أو **صوراً في «Fichiers»** (زر «احذفها من المتجر»، كلمة المرور الحساسة)، وصفحات منشورة اختفى قالبها (أعد نشرها). صفحة محذوفة تبقى زياراتها وطلبياتها في الأرقام، وسطرها في «الزوار والتحويل لكل صفحة» مخفي باسم «صفحة هبوط محذوفة» (زر «إظهارها»).

**الصور هي الصفحة** (مثل صفحات البيع الناجحة: خطاف ثم صور تشرح، لا صورة ثم فقرة ثم صورة): مع النص يخطط Claude من 5 إلى 7 صور **حسب تسلسل الزاوية المختارة**، كل صورة فكرة واحدة بنوعها: **الخطاف** (المنتج كبير مع لمسة الزاوية ووعدها)، **المشكلة** (كما يعيشها الزبون، لزاوية المشكلة)، **ميزة تُرى** (مثل ترمس مقلوب لا يسرّب، إن ذُكر في الصفحة)، **المزايا حول المنتج** (تسميات بجانب أجزائه)، **أثناء الاستعمال**، **النتيجة** (فرحة، راحة)، **هدية**، **ما تستلمه** (محتوى الطرد)، **تفصيل قريب**، **الحجم** (إن عُرف)، **الألوان** (الموجودة فعلاً). عنوان الصورة يقول معناها لا ما يُرى فيها، وأجوبتك تظهر تسمياتٍ وصور ميزة. لكل صورة مكان وزاوية كاميرا مختلفان (macro، close، medium، wide، top_down)، فلا تخرج الصور متشابهة.
- **الكتابة داخل الصورة افتراضياً**: العنوان في شريط بلون تصميم الصفحة (هدية وردي، المشكلة أخضر مزرق، يومي أزرق، قيمة ذهبي، عائلة بنفسجي) والتسميات بجانب ما تشير إليه، نفس الشكل في كل صور الصفحة. إن أخطأت الحروف العربية في صورة: أطفئ «الكتابة داخل الصورة» وأعد رسمها، فيظهر عنوانها نصاً حيّاً تحتها.
- «ارسم الكل» يرسمها مولّد الصور (الإعدادات ← الصور: Gemini، النموذج الافتراضي `gemini-nano-banana-2.1`، نحو 0.04$ للصورة بدقة 1K) **من الصورة الرئيسية للمنتج + وصف صفحته** (صورة الألوان ترى صور المنتج كلها حتى لا يخترع لوناً)، بتطابق كامل للشكل والألوان والطباعة، بنسبة 4:5، والأشخاص بلا وجوه ظاهرة (أيدٍ، من الخلف).
- **3 صور مكتوبة أو أكثر = صفحة بالصور**: الخطاف (عنوانه داخل الصورة، والنص الحيّ يُخفى بصرياً ويبقى للبحث) ← شريط الثقة ← 3 صور متتابعة ← خطوات الطلب ← **النموذج** ← بقية الصور ← الخصائص، الضمانات، التوصيل، الأسئلة، والزر. أقل من ذلك: تصميم الزاوية المعتاد بالفقرات.
- راجع كل صورة وأخفِ أو أعد رسم ما غيّر شكل المنتج (منتج لا يطابق الصورة = طرد مرفوض). عند النشر تُرفع الصور الموافق عليها مرة واحدة إلى «Fichiers» في Shopify (لا تدخل معرض المنتج). وبلوك «التوصيل والدفع» يحسب «من… دج» وعدد الولايات من جدول القالب الحي، فيبقى صحيحاً إن غيّرت الأسعار.

**صنعة الكاتب (أفضل مهارات التسويق، مدمجة في البرومبتات):** رسائل النظام الثلاث (تحليل المنتج، النصوص، خطة الصور) مبنية هكذا: `<role>` (من يكتب ولمن) ← `<craft>` (الصنعة) ← `<rules>` (حدود الصدق وسياسة Meta والدفع عند الاستلام) ← `<method>` (يفكر قبل الكتابة ويراجع بعدها: اختبار «الآن يمكنك…»، اختبار الاستبدال، علامات الكتابة الآلية، دليل لكل ادعاء)، والمعطيات في `<data>` منفصلة عن الطلب `<task>` فلا يصير نص المنتج تعليمات. الصنعة في `server/prompts/landing/{angles,copy,visuals}.md` بالعربية، مستخلصة من أكثر مهارات التسويق تثبيتاً على skills.sh (copywriting، marketing-psychology، ad-creative، image، product-marketing، cro) بطريقة مهارة Vercel `find-skills`، والمصادر والنسخ في `server/prompts/landing/SOURCES.md`. نفس الملفات في مهارة **`cod-landing-page-builder`** (`.claude/skills/`) مع برومبتات جاهزة لأي باني صفحات (n8n، محادثة، ERP آخر)، واختبار يمنع اختلافهما. لتعديل الصنعة: عدّل ملفات الـ ERP، انسخها إلى المهارة، `npm test`، ثم أعد رفع المهارة (`SKILLS.md`).

يحتاج تطبيق Shopify: `read_themes` و`write_themes` و`write_online_store_navigation` (و`write_files` للصور)، **موافقاً عليها في المتجر**: إضافتها في Dev Dashboard ثم Release لا تكفي؛ من متصفح: dev.shopify.com ← التطبيق ← «Install app» ← اختر المتجر ← وافق على الأذونات الجديدة.

## اختبار صفحات الهبوط A/B على نفس الدومين

1. أنشئ صفحات الهبوط من الـ ERP (صفحات المتجر ← «إنشاء صفحة هبوط» ثم «نشر على المتجر»)، أو قوالب منتج إضافية في محرر Shopify.
2. في الـ ERP: **اختبار الصفحات ← اختبار جديد** واختر المنتج، فيُبنى الاختبار تلقائياً:
   - رابط الدخول = صفحة المنتج `/products/<المنتج>`، وهو رابطك الرسمي في منشورات فيسبوك وإنستغرام.
   - النسخة A = صفحة المنتج نفسها، ثم **كل صفحات الهبوط المنشورة لهذا المنتج** باسم زاويتها، بحصص متساوية. مثلاً 3 صفحات هبوط + صفحة المنتج = 4 نسخ، لكل واحدة 25.
   - الحد 6 نسخ. يمكنك تعطيل نسخة أو تغييرها من القائمة، أو اختيار «رابط آخر».
   - صفحة هبوط نُشرت بعد إنشاء الاختبار يقترحها «تعديل» بزر «أضفها».
   - القائمة تضع الرابط النهائي `/products/<المنتج>?view=lp-<slug>`، لا التحويلة `/pages/…`.
   **النسبة** = من كل 100 زائر يفتح رابط الإعلان، كم يذهب لهذه النسخة (50 و50 = النصف لكل صفحة). اتركها متساوية طوال الاختبار.
3. **تثبيت على القالب** (مرة واحدة). يحتاج تطبيق Shopify الإذنين `read_themes` و `write_themes`: أضفهما في Dev Dashboard (Versions ← Release) **ثم وافق عليهما في المتجر** (افتح التطبيق من «Applications»)، فالإذن لا يعمل قبل الموافقة. إن نقص إذن يسمّيه الـ ERP بالاسم. وإن رفضت Shopify الكتابة رغم الإذنين (الاستثناء الذي تشترطه على تطبيقات التوزيع العام) يعطيك الـ ERP الكود والسطر لتلصقهما يدوياً في دقيقتين.
4. ضع **رابط الاختبار** في الإعلان: `/products/<المنتج>?erp_t=<اسم-الاختبار>`. كل زائر يأتي منه يرى نسخة، ويبقى عليها إن عاد، ورابط صفحته يحمل `erp_v=<اختبار>.<حرف>`.
   - **صفحة المنتج العادية لا تتغيّر أبداً:** من يتصفح المتجر من الأقسام، أو يفتح رابط المنتج دون `?erp_t=`، يرى صفحة المنتج الأصلية.
   - من يفتح رابط صفحة هبوط بعينها (`/pages/<slug>`) يبقى عليها، وتُعدّ زيارته وطلبيته لتلك الصفحة خارج حكم الاختبار.
   - **الطلبية تُنسب للصفحة التي أُرسل منها النموذج** (`landing_page` = رابط الصفحة عند الإرسال)، وللنسخة فقط إن حمل ذلك الرابط `erp_v`. لا يُعتمد `utm_content`: نموذج الطلب يحفظ آخر UTM في المتصفح، فمن مرّ بنسخة ثم طلب من صفحة أخرى كان يُحسب للنسخة الأولى.
   - utm_content الإعلان (اسم الإعلان) لم يعد يُستبدل.
   - بطاقة كل نسخة تعرض «الصفحة كلها» (كل زوارها وطلبياتها) ثم «من رابط الاختبار» (التي يدخلها الحكم).

- الإعدادات تُحفظ في metafield المتجر (`erp_toureche.splits`، النسخة 3)، فالاختبار يعمل **24/7 دون جهازك**.
- دون عنوان عام للـ ERP (تشغيل على الحاسوب) لا تُعدّ الزيارات، ويحكم الـ ERP بالطلبيات مقارنة بنِسب التوزيع (نموذج Poisson-Gamma).

### عدّاد الزوار المخفي (صفحات المتجر ← «الزوار والتحويل لكل صفحة»)

نفس السنيبت (`snippets/erp-split.liquid`) يعدّ زوار **كل صفحات المتجر**: الرئيسية، المجموعات، صفحات المنتجات، وصفحات الهبوط.

- كل صفحة ترسل زيارة واحدة إلى الـ ERP (`/api/hooks/sp/<المشروع>`، عبر `sendBeacon`، لا يؤخر الصفحة)، و«بدأ النموذج» عند أول لمسة لنموذج الطلب.
- الزائر يُعدّ مرة واحدة لكل صفحة في اليوم. لا تُعدّ الروبوتات (زاحف Meta، Google، PageSpeed…)، ولا محرر القالب، ولا الصفحات المحمّلة مسبقاً قبل فتحها.
- **لا تعدّ زياراتك أنت:** افتح `https://<متجرك>/?erp_me=1` مرة واحدة على كل هاتف أو حاسوب تستعمله (الرابط في البطاقة).
- **الزوار الآن** (بطاقة في أول صفحات المتجر، وشارة «● N الآن» في «اليوم»): عدد الأشخاص الفريدين الذين دخلوا صفحة أو لمسوا النموذج في آخر 5 دقائق، يتجدد كل 10 ثوانٍ، ومعه من يملأ النموذج الآن ومن جاء من إعلان وآخر 30 دقيقة واليوم والصفحات المفتوحة. ويليه **متى يدخل الزوار وتأتي الطلبيات**: 24 ساعة بتوقيت الجزائر في آخر 7/14/30 يوماً، أكثر الساعات دخولاً وأفضل نافذة من 3 ساعات وأكثرها طلباً (لاختيار ساعات الاتصال بالزبائن والنشر). أقل من 50 زائراً: يقول إن البيانات قليلة ولا يعطي رأياً.
- لكل صفحة: الزوار، من بدأ النموذج، الطلبيات، **التحويل** (طلبيات ÷ زوار)، والمسلّمة. ومعها مصادر الزوار (إعلانات Meta، الشبكات، البحث، التنقّل الداخلي، المباشر) ومنحنى يومي.
- **التحديث تلقائي:** عند تشغيل الـ ERP بعد كل تحديث، ثم كل 6 ساعات، يقارن السنيبت المثبت بنسخته ويحدّثه وحده إن تغيّر. التثبيت أول مرة (أو قالب جديد) يبقى قرارك: اختبار الصفحات ← «تثبيت على القالب» (كلمة المرور الحساسة).
- البطاقة تعرض «آخر زيارة قبل…»: إن لم تصل زيارة منذ يوم كامل فالعدّاد لا يعمل.
- الزيارات تُحذف بعد 400 يوم.
- سياسة Meta: كل النسخ = نفس المنتج ونفس العرض. لا cloaking (روبوتات Meta توجَّه بنفس التوزيع).
- **صفحة هبوط سُحبت أو حُذفت** تتوقف نسختها في الاختبار تلقائياً. ونسخة غاب قالبها `product.lp-…` عن القالب المنشور (تغيير القالب مثلاً) لا يُوجَّه إليها أحد، وتظهر في بطاقة «التكامل مع القالب» حتى تعيد نشر الصفحة أو تنهي الاختبار.

## تتبّع الأحداث: المتجر + n8n + الـ ERP (بيكسل SOU9NA)

| الحدث | من يرسله | متى |
|---|---|---|
| PageView · ViewContent | بيكسل المتجر (`assets/meta-events.js`) | كل صفحة / صفحة منتج |
| InitiateCheckout · AddToCart · AddPaymentInfo | بيكسل المتجر (`assets/cod-form.js`) | أول لمسة للنموذج · اختيار عرض أو نوع · الاسم والهاتف والولاية صحيحة |
| **Purchase** | بيكسل المتجر **و** n8n (Conversions API) **بنفس event_id** | إرسال النموذج — Meta تحسبه مرة واحدة |
| **OrderConfirmed** | الـ ERP (CAPI، `phone_call`) | تأكيد المؤكِّد بالهاتف (يُفعَّل في بطاقة Meta) |
| **OrderDelivered** | الـ ERP (CAPI، `other`) | التسليم والدفع عند الباب (يُفعَّل في بطاقة Meta) |

- حدثا الـ ERP مربوطان بالطلبية الأصلية (`original_event_data`: Purchase + `event_id` + `order_id`)، فتنسبهما Meta إلى نفس الإعلان ولو بعد أيام. الـ ERP يأخذ `event_id` من خاصية الطلبية في Shopify (يضعها n8n) أو من عمود `event_id` في الجدول.
- هوية الزبون مجزّأة بنفس طريقة نموذج المتجر (الهاتف `213…`، الاسم، البلدية اللاتينية) + الولاية، حسب قواعد Meta. وقت الحدث = لحظة التأكيد/التسليم (Meta ترفض ما تجاوز 7 أيام).
- لا يُرسل الحدث مرتين (التراجع عن الحالة ثم إعادتها)، ولا لطلبية هاتفية يدوية بلا صفحة هبوط. النتيجة في سجل الطلبية: «وصل» / «تجربة» / الخطأ.
- **التجربة:** رمز «اختبار الأحداث» في بطاقة Meta يرسل أحداث الـ ERP إلى Test events فقط، ويتوقف **تلقائياً بعد 3 ساعات** من حفظه (نسيانه كان يحوّل كل أحداث الإنتاج إلى تبويب الاختبار بصمت)، والإعدادات تعرض ساعة توقفه، والمستشار ينبّه ما دام موجوداً. طلبياتك التجريبية من المتجر تصل إلى Meta كـ Purchase حقيقي: جرّب بعد وضع نفس الرمز في n8n (`metaTestEventCode` في عقدة Config) ثم امسحه.
- **تنبيهات الربط:** فحص يومي للرمز (يعمل دون المزامنة التلقائية) يحفظ تاريخ انتهائه؛ «اليوم» والمستشار والقرارات تنبّه قبل **14 يوماً** (حرج قبل 3)، وعند انتهائه أو موته، وعند نسيان رمز الاختبار. «اختبار» في بطاقة Meta يحدّث الحالة، ورمز جديد يمحو التنبيه القديم.
- **جاهزية الإطلاق** (الإعلانات ← صحة الحسابات): 15 بنداً بحالة واضحة (جاهز/تنبيه/يمنع/لم يُفحص) وما يجب فعله لكل واحد: Shopify، منتج منشور، صفحات المنتجات (بيكسل ونموذج صحيحان)، رمز Meta وأيامه، الحساب الإعلاني، البيكسل يستقبل، رمز أحداث الـ ERP، رمز الاختبار، سعر الصرف، عدّاد الزوار، نسب الطلبيات، شركة توصيل، نسخة احتياطية. وتحتها تذكيرات يدوية لما لا يراه الـ ERP (رمز n8n، حالة التطبيق Live).
- **تكلفة المسلّمة لكل حملة** (الإعلانات ← الحملات، عمود «الـ ERP: طلبيات · مسلّمة»): الطلبيات تحمل `utm_campaign` = معرّف الحملة (من «معاملات URL» التي يضعها الـ ERP)، فتُحسب لكل حملة طلبياتها ومسلّمتها وما في الطريق، وتكلفة المسلّمة = الإنفاق ÷ (المسلّمة + ما في الطريق × نسبة التسليم) مقابل حد التعادل لمنتجها (أخضر ≤ 60%، أصفر ≤ 105%، أحمر فوق ذلك، ولا حكم قبل 3 مسلّمة). حملات أُنشئت خارج الـ ERP دون هذه المعاملات لا تظهر لها طلبيات.
- **لا تثق بنجاح تنفيذ n8n:** عقدة CAPI مضبوطة «تابع عند الخطأ»، فخطأ Meta (100/33 مثلاً) لا يُظهر التنفيذ فاشلاً ولا يوقظ «مراقب الأخطاء». المرجع مخرجات عقدة «Meta Conversions API»: `events_received: 1`.
- **ذاكرة UTM في المتصفح لا تنتهي:** نموذج الطلب يحفظ آخر UTM في `localStorage` بلا مدة، فكل طلبية لاحقة من الجهاز نفسه ترثه (طلبياتك التجريبية كلها حملت `utm_content=thermos-c` حتى لمنتج آخر). n8n يفضّل UTM الرابط الحالي على المحفوظ. لا تحكم على إعلان بطلبيات من جهازك.
- **في Ads Manager:** أنشئ «تحويلاً مخصصاً" (Custom conversion) لكل من OrderConfirmed وOrderDelivered لترى «تكلفة الطلبية المؤكدة/المسلّمة» لكل إعلان. التحسين عليهما لاحقاً عندما يصل الحجم (Meta تنصح بنحو 50 حدثاً أسبوعياً لكل مجموعة)؛ قبل ذلك يبقى التحسين على Purchase.

## قواعد الإعلانات المطبّقة (حسب Meta)

- تغيير الميزانية بنسبة كبيرة قد يعيد المجموعة إلى **مرحلة التعلم** (Meta Business Help: *Significant edits and the learning phase*). الـ ERP يقترح **+20% كحد أقصى** في كل مرة، ثم الانتظار 3–4 أيام، ويطلب تأكيداً صريحاً لأي تغيير أكبر.
- تعديل الجمهور أو التصميم، إضافة إعلان، تغيير المزايدة، أو الإيقاف 7 أيام فأكثر = تعديل جوهري ← تحذير قبل الحفظ.
- حالة التعلم لكل مجموعة (`learning_stage_info`) ظاهرة في المستكشف.
- الحكم على المنتج = **تكلفة الطلبية المسلّمة** مقابل **حد التعادل** (السعر − التكلفة − التغليف − حصة المرتجعات)، لا مشتريات البيكسل.
- الحملات تُنشأ **متوقفة** للمراجعة؛ التفعيل والميزانيات بكلمة المرور الحساسة؛ الميزانية لا تُخمَّن أبداً.
- **رابط الإعلان يُفحص قبل الإطلاق** كما يفتحه زائر من هاتفه: يفتح (لا 404)، دون تحويل، الرابط الأساسي (canonical)، بيكسل الحملة، نموذج الطلب، المخزون، السرعة. صفحة مكسورة أو نفد مخزونها أو تحويلات لا تنتهي = لا إطلاق؛ الباقي تنبيهات، و«استعمل الرابط النهائي» يصحح التحويل بنقرة.
- الرابط يبقى **صفحة المنتج نفسها** والتتبّع في «معاملات URL» (`url_tags`) بمعاملات Meta الديناميكية: `utm_source={{site_source_name}}` (fb/ig/msg/an/th) و`utm_campaign={{campaign.id}}` و`utm_term={{adset.id}}` و`utm_content={{ad.id}}`، فتُنسب كل طلبية إلى إعلانها. تُكتب عند الإنشاء لأن تغييرها بعد النشر يعيد المجموعة إلى مرحلة التعلم.
- **زر الدعوة:** يُختار من قائمة Meta (أو يُكتب رمز نوع آخر منها، مثل `VIEW_PRODUCT`، أو «بلا زر»)، ويُتحقق منه قبل إنشاء أي شيء. نص الزر نفسه تحدده Meta بحسب النوع ولغة المشاهد ولا يقبل نصاً حراً؛ **العبارة الحرة تُكتب في «العنوان»** وتظهر بجانب الزر كما كُتبت. يُعدَّل الزر والعنوان على إعلان منشور من تحرير الحملة (تصميم جديد تراجعه Meta).
- **منشور صفحة موجود:** إن حمل رابط المتجر يُستعمل كما هو بتفاعلاته؛ وإن كان صورة ونصاً بلا رابط (الغالب) فتُبنى منه إعلان رابط (صورته ونصه + الزر + رابط المنتج)، لأن Meta ترفض حملة طلبات بلا رابط موقع. الفيديو بلا رابط يُرفض برسالة واضحة. أي فشل بعد إنشاء الحملة يحذف الحملة والمجموعة ولا يُسجَّل شيء.
- الإعلان الرئيسي على رابط المنتج المباشر (الدومين الموثّق)، لا على `/go/…` ولا `?erp_t=`: كل تحويل يؤخر الزائر ويُفقد «مشاهدات الصفحة» التي تحسبها Meta.

## الأمان · Sécurité

- كلمة مرور دخول + **كلمة مرور حساسة** منفصلة للحذف والأسعار والميزانيات وتفعيل الحملات والإعدادات.
- المفاتيح السرية مشفّرة AES-256-GCM ولا تُعرض بعد حفظها. احفظ نسخة من `data/.secret-key`.
- جلسات httpOnly + SameSite=Strict، حماية CSRF، قفل بعد محاولات خاطئة، سجل نشاط كامل.
- نسخة احتياطية كل ليلة في `data/backups` (آخر 14 يوماً) + نسخة خارج الجهاز: Google Drive عبر n8n على الـ VPS، أو مجلد سحابي عبر `ERP_BACKUP_MIRROR` على حاسوب (انظر أدناه).
- نسيت كلمة المرور؟ `npm run reset-password -- اسم_المستخدم كلمةجديدة123` أو `npm run reset-password -- --sensitive كلمةجديدة123`.

### الأدوار (الإعدادات ← المستخدمون) — الخادم يفرضها، لا الواجهة فقط

| الدور | ماذا يستطيع |
|---|---|
| **المدير** | كل شيء: الإعدادات، المستخدمون، نشر صفحات الهبوط وحذفها، **الحذف الجماعي** |
| **المسؤول** | المنتجات، إنشاء صفحات الهبوط، الإعلانات، المالية — دون الإعدادات والمستخدمين ونشر الصفحات والحذف الجماعي |
| **موظف التأكيد** | الطلبيات فقط (تأكيد، لا يرد، الشحن، الملاحظات) والقائمة السوداء؛ لا يعدّل المنتجات ولا الإعلانات ولا ينفق على الذكاء الاصطناعي |
| **مشاهد** | يرى كل الأقسام ولا يغيّر أي شيء |

كلمة المرور الحساسة تُطلب **كل مرة** حتى للمدير (لا نافذة «تذكّرني» افتراضياً)، فلا تعطها لأحد.

### الحذف الجماعي (الطلبيات، الزبائن، السلات المتروكة)

حدّد الأسطر ← «حذف» ← بطاقة تشرح ما سيحدث بالضبط ← إن كان كل ما في القائمة محدداً: تحذير إضافي «أخطأت / نعم متأكد» ← كلمة المرور الحساسة. الحذف من الـ ERP فقط (طلبية Shopify تبقى)، ومرجع كل طلبية محذوفة يُحفظ فلا تعيدها مزامنة Shopify ولا الجدول ولا n8n. حذف زبون = حذف كل طلبياته في المشروع المختار؛ القائمة السوداء تبقى. كل حذف في سجل النشاط، والنسخة الليلية تحفظ ما قبله.

## إن تعطّل الجهاز · Si l’ordinateur lâche

الكود محفوظ في GitHub، والبيانات (الطلبيات، الزبائن، الإعدادات) تُنسخ كل ليلة إلى مجلد Google Drive أو OneDrive أو iCloud.

**مرة واحدة الآن:** ثبّت تطبيق Google Drive (أو OneDrive) على الجهاز، ثم أضف إلى ملف `.env`:

```bash
ERP_BACKUP_MIRROR='G:\My Drive\ERP-backups'                                   # Windows (Google Drive)
ERP_BACKUP_MIRROR='~/Library/CloudStorage/GoogleDrive-…/My Drive/ERP-backups'   # macOS
```

أعد التشغيل ثم اضغط **الإعدادات ← النظام ← نسخة احتياطية الآن**: يجب أن تظهر «يعمل». واحفظ محتوى `data/.secret-key` في مدير كلمات المرور.

**على جهاز جديد:**

```bash
git clone https://github.com/ouss-trch/my-profil.git
cd "my-profil/ERP TOURECHE"
npm run setup
npm run restore -- "<مسار آخر ملف toureche-YYYY-MM-DD.db من المجلد السحابي>"
# ضع ملف .secret-key القديم داخل data/ (وإلا أعد إدخال مفاتيح الربط من الإعدادات — الطلبيات والزبائن لا تتأثر)
npm start
```

نفس المستخدمين وكلمات المرور. `restore` يتحقق من الملف ويحفظ القاعدة السابقة قبل الاستبدال.

**إن تعطّل الـ VPS:** ثبّت الـ ERP على خادم جديد (قسم الـ VPS أعلاه)، نزّل آخر ملف `toureche-YYYY-MM-DD.db.gz` من مجلد `TOURECHE-ERP-backups` في Google Drive وانقله إلى الخادم، ثم:

```bash
erp restore /root/toureche-2026-10-27.db.gz     # يقبل الملف المضغوط كما هو
erp import-key /root/.secret-key                # من مدير كلمات المرور
```
